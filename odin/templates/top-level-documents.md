# Templates: packet top-level documents

Skeletons for every required document at the root of `findings/`. Adapt freely; keep
the substance each one must carry. `ACTION_MANIFEST.json` and `MANIFEST.sha256` are
generated by the toolkit and are not templated here.

---

## `README.md`: the packet guide

```markdown
# Findings packet

Evidence packet for **<repository name>**, produced by odin.

## What this is

A read-only forensic analysis of one repository: an exhaustive file inventory, per-file
and per-module documentation, architecture synthesis, dependency and SBOM data,
security findings, test and coverage evidence, and a manifest of every action taken.

## How it was produced

- Repository revision: `<git HEAD>` (`<clean|dirty>`)
- Files inventoried: N (M regular files, K directories)
- Analysis: static <plus sandboxed dynamic | only: dynamic analysis was skipped, see ERRORS.md>
- Network policy: <denied | advisory-only | authorized>
- Repository integrity after analysis: <PASS|FAIL>

## How to read it

| Start here | For |
| --- | --- |
| `EXECUTIVE_SUMMARY.md` | the whole picture in one page |
| `REPOSITORY_OVERVIEW.md` | what the project is and how it is organized |
| `ARCHITECTURE.md` + `graphs/` | how it fits together |
| `BUILD_AND_RUN.md` | building, running, debugging, deploying |
| `SECURITY.md` | security posture and findings |
| `TESTS_AND_COVERAGE.md` | test status and measured coverage |
| `DEPENDENCIES.md` | the supply chain |
| `files/` and `modules/` | the per-file and per-module record |
| `ASSUMPTIONS_AND_LIMITATIONS.md` | what this packet does **not** establish |
| `REPRODUCE.md` | reproducing the analysis |
| `ACTION_MANIFEST.json` | every action attempted or skipped |

## Conventions

Conclusions are labeled OBSERVED, DECLARED, DERIVED, DOCUMENTED or INFERRED. Secret
values are never reproduced. Coverage numbers appear only where coverage was measured.
```

## `EXECUTIVE_SUMMARY.md`

```markdown
# Executive summary

**Status:** complete | partial
**Repository integrity after analysis:** PASS | FAIL

## What this repository appears to do

Two or three concrete sentences, with the evidence class behind the claim.

## Size and shape

N files inventoried (M regular, K directories), X MB, Y lines of text.
Primary languages: …  Applications/services/libraries/modules: …
Architectural style: … (evidence)

## Entry points

The principal ones, with evidence.

## Build and run

How it is built; how it is run. Which commands were verified and which are UNVERIFIED.

## Dependencies

Ecosystems, direct/transitive counts, how many versions resolved exactly versus
remained constraints, unresolved external artifacts.

## Tests and coverage

Executed / not executed and why. Passed / failed / skipped counts if executed.
Measured coverage, or "not measured": never a number you did not measure.

## Most important security findings

Ranked, each in one line with severity and confidence.

## Most important correctness and quality findings

## Most important unfinished work

## Dynamic analysis

Performed vs skipped, with the sandbox and network policy that applied.

## Major contradictions and unknowns

Where the repository contradicts itself, and what could not be determined.

## Reproducibility

What reproduces exactly, what does not, and why.

---

No tool finding "nothing" is not evidence of safety, completeness or correctness. See
`ASSUMPTIONS_AND_LIMITATIONS.md` for what this analysis does not establish.
```

```markdown
# Assumptions and limitations

## Assumptions

| # | Assumption | Why it was needed | Evidence it rests on | Impact if wrong |
| --- | --- | --- | --- | --- |
| A1 | `main` is the default branch | no remote HEAD available offline | INFERRED from `.git/HEAD` | branch-specific conclusions |

## Ambiguities and contradictions found

| # | Contradiction | Evidence A | Evidence B | Resolution |
| --- | --- | --- | --- | --- |

## Work skipped, and why

| Work | Reason | Manifest action |
| --- | --- | --- |
| Dynamic test execution | no adequate sandbox available | `DYN-001` blocked_by_policy |

## Analysis limitations

- Coverage of the analysis itself: which languages got semantic parsing, which got
  structural or lexical only.
- Tools that were unavailable and what that leaves unknown.
- Scan caps that applied (file size, per-file match limits).
- What was not analyzed at all.

## What this packet does not establish

Plain statements. "No SAST tool supported the Kotlin sources, so no automated source
security analysis covered 18% of the first-party code."
```

## `REPRODUCE.md`

```markdown
# Reproducing this analysis

## Environment recorded at analysis time

OS, architecture, sandbox implementation, network policy, tool and runtime versions -
see `inventory/environment.json` for the full list.

## Repository state

VCS type, HEAD revision, clean/dirty, submodule state: see `inventory/vcs-state.json`.
Reproduction requires the same revision **and** the same working-tree state; a dirty
tree at analysis time cannot be reconstructed from the revision alone.

## Determinism settings applied

`TZ=UTC`, `LC_ALL=C.UTF-8`, `LANG=C.UTF-8`, `PYTHONHASHSEED=0`, `umask=022`, plus
anything that could not be applied (recorded in the state file).

## Steps

```
odin.py init --repo <REPO_ROOT> --artifacts <ARTIFACT_ROOT> --network <policy> --sandbox <kind>
odin.py env
odin.py inventory
... the exact sequence from ACTION_MANIFEST.json ...
odin.py verify
odin.py validate
odin.py manifest
odin.py package
```

## What reproduces exactly

The inventory, hashes, classification, scans, per-file document skeletons, manifest
digests, and the ZIP itself: packaging is byte-identical for identical content.

## What does not reproduce exactly

| Source of nondeterminism | Observed effect | Seed/options recorded |
| --- | --- | --- |

## Reproducibility classification

`byte-identical demonstrated` | `content-equivalent` | `partially reproducible` |
`not reproducible`: with the evidence for the claim. Do not claim byte-identical
reproducibility that was not actually demonstrated.
```

## `TESTS_AND_COVERAGE.md`

```markdown
# Tests and coverage

## Test inventory

Frameworks detected, test files, test counts by suite, how they are invoked, what CI
runs.

## Execution

Executed in <sandbox> | **not executed** because <reason>.

| Suite | Discovered | Selected | Passed | Failed | Skipped | XFailed |
| --- | --- | --- | --- | --- | --- | --- |

Collection failures are counted separately from test failures, and missing-dependency
failures separately from product failures.

## Failures

Summarized here; full sanitized diagnostics in `tests/failures.md`.

## Flakiness and nondeterminism

Anything observed, with evidence.

## Coverage

**Measured:** yes/no. If yes: tool and version, what was instrumented, and the
numbers. If no: say so plainly: not measured is not zero percent.

## What the tests do not cover

Read from the test inventory, not from coverage numbers alone.
```

## `SECURITY.md`, `DEPENDENCIES.md`, `ARCHITECTURE.md`, `BUILD_AND_RUN.md`, `REPOSITORY_OVERVIEW.md`, `TODOS_AND_UNFINISHED_WORK.md`

These are driven by their phase references rather than a fixed skeleton:

| Document | Reference |
| --- | --- |
| `SECURITY.md` + `security/SECURITY_NOTES.md` | `reference/security.md` |
| `DEPENDENCIES.md` | `reference/dependencies-and-sbom.md` |
| `ARCHITECTURE.md` | `reference/architecture.md` |
| `BUILD_AND_RUN.md`, `REPOSITORY_OVERVIEW.md` | `SKILL.md` Phase 4 |
| `TODOS_AND_UNFINISHED_WORK.md` | `SKILL.md` Phase 3 + `static-analysis/unfinished-work.json` |

Each one carries evidence labels on its claims, marks unexecuted commands
`UNVERIFIED`, and reports conflicts rather than resolving them silently.
